# RN-20260817-002｜Batch 2：现状基线 / 人工参照系 / 工作行为轨迹

## Question
把 FDE OS 当前缺位的三个交付前置件做成可执行方法与最小工具：现状基线（Baseline）、人工参照系（Human Benchmark）、工作行为轨迹（Work Trace），并区分「业务逻辑」与「系统摩擦」（Issue #1）。

## 第一轮｜系统内部核对（结论：三者在 OS 内均为缺位或雏形）
- DEL-008（Baseline 阶段方法）/DEL-009（Work Trace 方法）均 Draft 缺位；G-03/G-04 为 P0。
- 雏形资产：手册规范 L2 准入八查含「能形成现状基线」（仅检查项，无方法）；R-C04 指标纪律（基线确认前指标只能作评估项）；作业-准入-01 B 节「真实事项」14 字段 = Work Trace 的字段雏形；网络货运回放 L87 列出基线四字段（审核量/单笔时间/异常比例/人工投入）但全部未测得；官网方法论「没有可靠基线时不写收益承诺」。
- 内部反例：结算协同案例的「耗时两天」是**单次记录，非统计基线**（audit 已判定）——证明「有数字≠有基线」。
- E248 复查（2026-08-17 第二次）：本地仍无转写。瓴羊投手案例继续缺席，本批不用瓴羊主张。

## 第二轮｜外部证据（三条主线，均为跨组织来源）

### 1. 基线方法（EV-EXT-004）
- AI 介入前先取四维基线：**成本、时长、质量、量**；基线必须**先于项目设立**，「上线后再发明指标」是企业常见失败模式（agility-at-scale、classicinformatics 等多源一致）。
- 纪律：项目启动前指定**单一具名业务指标**；预设成功窗口（30/60/90 天）。学术侧证：arXiv 2512.04123《Measuring Agents in Production》（306 名从业者+20 案例研究）。
- **判定**：跨组织多源一致 → 方法层 OBSERVATION；具体四维框架采信为我们的 DESIGN DECISION（L2/L3 佐证）。

### 2. 人工参照系与 Golden Case（EV-EXT-005）
- 标注前先跑**试标注轮**校准标注者、迭代指南；目标**经机会校正的一致率 IAA ≥ 0.8**（Cohen's/Fleiss' κ，原始一致率在不平衡数据上会误导——全判「通过」也能到 90%）；**分歧是诊断信号**：通常暴露任务或判据含糊，而非标注者失误；僵持分歧用**第三人仲裁**；Golden Dataset 宜小而多样（Booking.com、Maxim、Arize、Galtea 多源一致 + arXiv 2506.13023）。
- **判定**：测量方法学（κ/IAA/仲裁）为成熟方法 FACT；「≥0.8 目标」为行业惯例 OBSERVATION（非硬规则）；**「不能拿最厉害员工当 Ground Truth」获得方法论支撑**——单人无一致性可测，且优秀者的隐性判断需多案例多标注者才能显性化。

### 3. Work Trace 与任务挖掘（EV-EXT-006）
- 流程挖掘（Process Mining）：系统事件日志（ERP/CRM），端到端；任务挖掘（Task Mining）：用户级交互数据（点击/键入/工具切换），暴露**系统事件之间**发生的事——变通动作、手工返工、跨应用复制粘贴、影子 Excel（Signavio/Appian/UiPath/Paxray/ABBYY 多源一致）。
- 对 Issue 核心要求的直接支撑：观察数据须三分类——**业务规则候选 / 系统摩擦（不应教给 Agent）/ 混合待核**。
- **反向发现（对抗审查产出）**：不能把一切偏离系统的动作都判为摩擦——**影子表格可能承载未成文的真实业务规则**（规则在某系统外运行恰说明系统没接住它）。判定字段必须允许「混合待核」并在 Bad Case Review 中复核。

## Contradictions / 反例
1. 内部反例：结算协同「耗时两天」单样本被当典型情况描述——工具必须强制统计窗口与样本量字段，防单点冒充基线。
2. 外部陷阱：原始一致率≠一致性（不平衡数据）；基线事后发明≠基线。
3. Work Trace 观察悖论：被观察者会改变行为（霍桑效应）——首日观察记录仅作熟悉材料，不作为轨迹数据（写入工具 Hold 条件）。

## Implications（写入系统的最小集）
- DEL-008/009 从缺位升级为「方法草案已建（Designed-草案）」；不新增 Rule ID（最小侵入）。
- 新增 TOOL-004/005/006 三份草案（含 Hold 条件），交付物互链：Work Trace 产出→喂 Benchmark 选例；Benchmark 产出→Eval 黄金集底稿；Baseline→GATE-2 证据。
- 三者关系一句话：**基线回答「现在多差/多慢/多贵」，参照系回答「人能做到多好、好在哪里」，轨迹回答「人具体怎么做」——分别服务 ROI 口径、Eval 标准、Agent Skill 与工作流来源。**

## Dry Run｜网络货运支付前智能审核（真实项目，只验工具指导性，不虚写实施）
- **Baseline Sheet（TOOL-004）**：四维字段逐项填入→当前**全部为「未测」**；工具立即产出缺口清单：①近 3 个月审核单量与人均日处理量（口径：含/不含退回件）②单笔耗时分布（中位数/P90，非均值）③异常率按 15 条规则分桶④人工投入人日/成本。→ **结论：工具有效**——它把「方案建议 200-500 笔样本」细化为可执行的测量任务与口径问句。
- **Human Benchmark Sheet（TOOL-005）**：前置检查失败——15 条审核规则原文及责任部门确认**未取得**（台账 P0 既知缺口）；回放中的 AI 必要性逐项判定（证件/距离/重复/非标凭证）可直接转为 benchmark 候选题干，但缺「双人独立判定」环节。→ 工具正确阻止我们在材料不足时造标准。
- **Work Trace Sheet（TOOL-006）**：现有「材料获取-识别-核验-分级-人工确认-回传」链路出自**方案设计而非行为观察**（对抗点 C：不得当轨迹证据）；工具指示的下一步：观察 1 名审核员完整处理 3-5 笔真实订单，记录查看顺序/暂停点/工具切换/求助对象，按三分类标注每个动作。
- **总判定**：三表均把「下一步收集什么、问什么、记录什么」变成明确任务——满足 Issue 验收第 5 条。**未发生的事情一律标注「未测/未取得」，本 dry run 为纸面推演。**
